# 화면 공유 데모 순서

약 5분. 콘솔: http://localhost:18888

## 시작 전

Docker Desktop을 켠 뒤 콘솔을 실행하고, 브라우저에서 위 주소를 연다.

```bash
python demo/console.py
```

- **초기화**를 눌러 깨끗한 상태로 만든다. 30초쯤 걸린다.
- 처음에 "연결 안 됨"으로 보이면 **초기화**를 누르면 된다.
- 콘솔은 aws, 온프레, gcp 세 대를 띄운다. 온프레는 `onprem/` 구성 그대로다.
- 끝나면 `demo` 폴더에서 `docker compose -f docker-compose.yml -f onprem.compose.yml --env-file onprem.env down -v`로 정리한다.

## 정상 이전: aws → 온프레 → gcp (4분)

동기화 버튼은 현재 활성 환경에서 갈 수 있는 대상마다 하나씩 나온다. 다음 경로의 버튼이 파란색이다.

| 누를 것 | 볼 곳 | 설명 |
| --- | --- | --- |
| 부하 시작 | 응답 시간 그래프 | 사용자 12명이 로그인, 조회, 공구 참여를 계속 한다. 앱은 Redis 주소로 프록시만 안다 |
| 동기화 시작 (aws → onprem) | Sync Worker 줄, 온프레 키 수 | 알림 구독을 먼저 확인하고 양쪽을 스캔해 복사한 뒤, 쓰기를 멈추지 않은 채 전체를 비교한다. 앱은 계속 aws를 쓴다. `rl`은 일부러 복사하지 않아 온프레에서 0으로 남는다 |
| 컷오버 | 프록시, 단계 표, 그래프 | 키 수를 확인하고 → 쓰기를 멈추고 → 전체 비교 뒤 바뀐 키만 복사·검증하고 → 샘플을 확인하고 → 대상을 바꾸고 → aws 쓰기 권한을 회수하고 → 역방향 동기화를 켠 뒤 재개한다 |
| (그대로 둠) | 그래프, 큐 숫자 | 쓰기 정지 수십~100ms 정도. 실패가 0이다. 큐는 원본을 다 비운 뒤 consume이 온프레로 넘어간다 |
| 커밋 | 기록 | 첫 구간을 확정한다. 역방향 동기화가 멈춘다 |
| 동기화 시작 (onprem → gcp) → 컷오버 | 프록시, 세션 유실 | 같은 도구, 같은 절차로 온프레에서 gcp로 옮긴다 |
| 정상 롤백 | 프록시, 세션 유실 | 같은 절차를 반대 방향으로 실행한다. 온프레로 돌아와도 세션이 유지된다 |
| 동기화 시작 (onprem → gcp) → 컷오버 → 커밋 | 기록 | 다시 gcp로 옮겨 이전을 확정한다 |
| 검증 | 검증 결과 표 | 부하를 멈추고 완료 기준을 확인한다: 실패, 세션, 쓰기 차단, 삭제 반영, 캐시, 재고, 큐 유실, 처리 순서 |

## 장애 롤백 (2분)

초기화 → 부하 시작 → 동기화 시작 (aws → onprem) → 컷오버 후 진행한다.

| 누를 것 | 볼 곳 | 설명 |
| --- | --- | --- |
| 장애 주입 | 실패 그래프, p99 | 온프레 Redis를 kill한다. 호출이 실패하거나 프록시의 3초 제한까지 기다린다 |
| 장애 롤백 | 단계 표 | 최종 정리를 건너뛰고 aws로 전환하고, 쓰기 권한을 복구하고, 캐시를 지운다. 쓰기 정지는 수십 ms에서 최대 약 300ms |
| (그대로 둠) | 그래프 | 몇 초 뒤 응답 시간이 평소로 돌아온다. 롤백 전에 보낸 요청은 3초 제한 뒤 실패로 집계될 수 있다 |
| 검증 | 검증 결과 표 | 롤백 뒤 보낸 요청의 실패 0건, 큐 요청 유실 없음(DB의 QUEUED로 복구), 캐시 = DB |

## 받을 만한 질문

- **그래프 수치가 왜 40~50ms인가요?** 로컬 앱과 부하기까지 포함한 값이다. 절대값보다 전환 전후가 같은지를 본다.
- **실제 클라우드인가요?** 아니다. Valkey 컨테이너 3대가 AWS·온프레·GCP 역할을 하고 DB는 SQLite다. DB 컷오버와는 연결하지 않았다.
- **쓰기 정지 시간은 실제로도 이 정도인가요?** 이 화면은 키 수십 개 기준이다. 왕복 30ms를 흉내 내고 재면 키 10만 개에 약 1.6초였다(`demo/bench-results.jsonl`). 실제 클라우드 값은 아니다. 0단계에서 계산해 예산을 넘으면 시작하지 않는다.
- **전체 비교를 쓰기 멈춘 뒤에 안 하면 위험하지 않나요?** 그 뒤 바뀐 키는 알림으로 전부 받으니 그 키만 다시 보면 된다. 구독이 끊기면 전체 비교부터 다시 한다. 알림 없이 대상만 바뀐 값은 샘플에 안 걸리면 놓칠 수 있고, 이건 감수한 위험이다.
- **장애 롤백 유실은?** 역방향으로 아직 못 옮긴 키만큼이고, 화면의 "유실 범위"가 그 값이다. 로컬에서는 매번 0이라 실제 유실은 재현하지 못했다.
- **전환 도중에 실패하면요?** RESUME 전이면 대상에 쓴 것이 없어 활성 대상과 권한을 되돌리고 재개한다. `python demo/faults.py`가 이 경로들을 일부러 일으켜 확인한다.
- **RIOT을 왜 안 쓰나요?** 복제는 대체할 수 있다. 전환, 단일 쓰기 보장, 롤백, 큐 처리는 RIOT 범위 밖이다.
